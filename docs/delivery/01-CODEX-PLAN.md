# Delivery 01 · 分阶段开发与Codex交付计划

所有阶段是未来实施任务，本轮只完成设计。不得将整包当成“一次性把六工具全部做完”的指令。每次完成一个里程碑并提交证据后停止。

## 1. 工作方式

开始：读取AGENTS、当前阶段、相关工具、资金规格和最新远端。创建小分支；保持任务边界。结束：列出改动文件、实现内容、实际测试、未通过/NOT RUN、commit、下一阶段；不要继续隐式扩展。

所有实作使用PR与阶段验收。纯文档设计提交不创建应用占位代码。遇到真实资金或生产配置所需未知信息，记录门禁并继续可完成的本地/测试工作，不伪造凭证，也不把未授权操作称已完成。

## 3. M0必须回答的问题

主/测试网络chainId是否匹配？USDC接口的decimals/balance/allowance与SafeERC20调用是否按预期？实际receipt中的业务/底层事件怎样编码？EOA/ERC1271/钱包切链怎样工作？Gas预算与错误处理是否可用？

Workers构建产物能否路由API而不被SPA吞掉？D1 batch失败是否回滚？条件UPDATE0行如何防后续错误写入？outbox重放是否幂等？R2上传/私有下载及文件hash验证能否在资源限制内完成？受限证明签名与nonce调度是否可实现？

未通过就写明确结论/替代设计并修订ADR；不要生成大量上层代码掩盖基础失败。

## 4. 每阶段标准交付

设计到代码映射、变更文件清单、schema/ABI版本、可复现命令、真实结果、失败日志、风险、回滚方法。UI阶段提供实际渲染截图而非AI宣传图；合约阶段提供测试输出和资金向量；云阶段提供非秘密的部署清单与健康记录。

严禁把“测试文件已创建”写成“测试通过”，把“静态页面能打开”写成“支付已运行”，把“用户拒签”写成“链上交易失败”。

## 5. 可直接交给Codex的起始指令

> 在iwbinb/ArcBox读取AGENTS.md和docs。只实施M0技术验证，不一次开发整个产品；从最新main创建独立分支。先锁定版本、验证Arc网络/USDC/签名和Cloudflare核心能力；所有需真实资产或生产权限的步骤记录门禁，未经授权不执行。完成后提交探针、真实测试结果和文档修订，列出下一阶段，然后停止。

## 6. 分支/发布策略

main为受审查基线；每阶段feat/m0-validation等独立分支。PR描述使用需求/测试ID，避免夹带格式化全库。部署入口的环境清单按chainId/ABI/模板版本锁定。生产资金合约由单独发布任务管理，不随网页自动更新。

主网发布失败时不强行合并“临时绕过”；保持旧实例与既有资金退出路径，修复后新版本重新审查。
