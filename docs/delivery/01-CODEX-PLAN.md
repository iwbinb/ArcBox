# ArcBox 全阶段开发与部署总计划

版本：v1.1 · 2026-09-23  
性质：对现有设计与 M0—M10 开发计划的执行细化，按用户要求纳入仓库，替换本路径的 v1.0 执行计划。本次仅更新计划与文档入口，不代表新增功能、合并开发 PR 或完成部署；业务规则、付费资源及主网操作仍须到对应阶段分别确认。

## 1. 项目终点与执行原则

交付的是一个六工具集合站：交付收款 Deliver、成团收款 Group、合伙分账 Split、报名保证金 Attend、分阶段付款 Milestones、奖励领取 Rewards。六项均保留完整开发范围；先做三个工具的可运行版本，不意味着其余工具被取消。

最终交付包括网站、共享后台、六工具合约与接口、Cloudflare 基础设施、持续集成和受控发布、安全及恢复机制、实际测试证据、部署清单、使用与运维文档。是否允许接收真实资金，必须另外通过对应上线检查，不能由功能按钮是否齐全决定。

主路线：

> 技术底座 → 网站骨架与预览 → 共享后台与测试环境 → Split → Deliver → Group → 三工具受控主网版本 → Rewards → Attend → Milestones → 六工具完整发行与运维验收。

每个大阶段再拆成小交付。默认一次只执行一个明确子阶段；完成、测试、提交、汇报后停止。不能因为当前任务还有空间，就顺便开发下一工具。

## 3. 本次对旧计划的实质调整

### 3.1 保留编号，但拆开执行单位

M0—M10 的产品顺序不重编号。M0 拆 A—E；M1、M2 和工具阶段拆小交付。已有测试证据继续有效，不从头重做，也不把“一个 PR”强行等同于“整个大阶段”。

### 3.2 部署提前且分层

新增 D0—D3 四个部署检查点。先上线无资金预览，再建立完整测试环境，再批准三工具主网试运行，最后逐步开放完整六工具。不能等代码全部完成才发现账号权限、网络、文件访问或部署配置有问题。

### 3.3 技术探针不等于提前做完整业务系统

M0 验证最小技术能力；真实产品的 SIWE 会话、权限、多用户浏览器流程归 M2；实际账号中的 Cloudflare 资源验证归 D0/D1。原来笼统写在 M0 状态矩阵中的云端和完整浏览器项目，必须显式标记“迁至 D1 / M2 验收，未通过”，不能静默删掉或改成 PASS。

M0 本身仍需完成最小签名、测试网代币交易和 SDK/合约兼容探针。遇到真实测试网络或账号阻塞，记录影响；不得把模拟通过冒充线上通过。无关的无资金页面工作只有在明确调整排期后才能继续，不绕过资金相关门禁。

### 3.4 CI 与部署各有唯一入口

推荐 GitHub Actions 负责代码检查、测试、构建和受控调用 Wrangler；Cloudflare 负责网站和后端运行。不要同时启用 Workers Builds 与 Actions 对同一环境自动部署，避免重复发布和顺序竞争。Cloudflare 官方支持两条路径，本项目选择哪一条是工程决策，不是平台强制要求。[S1][S2]

### 3.5 正式规则确认在对应工具编码前

设计中给出的退款时长、上限、释放时点、争议超时、仲裁比例都是待确认的业务选择，不等于用户已经逐项批准。涉及资金后果时，在工具 A 子阶段列出最小决策卡再编码，不在上线前临时才发现规则有争议。

## 5. M0：技术底座的五次小交付

### M0-A：执行通道与只读探针 —— 已有证据通过

范围：写入工作流、push 触发、Runner 拉取准确 SHA、离线测试、测试网只读查询、读取日志。

边界：不能扩展成“所有 GitHub 管理接口、Cloudflare 权限或生产发布都已可用”。历史运行针对准确 SHA，不套用到后续代码。

### M0-B：开发工具链与 CI 基线 —— 下一项

工作：建立最小工程目录；锁定 Node/包管理器/TypeScript/构建和 Workers 测试依赖的可复现组合；加入 lockfile、秘密与生成物忽略规则；最小 Worker/静态资产构建；合约编译工具版本与校验；统一检查命令。该最小资产仅是编译探针，不构成未经确认的产品 UI。

CI 将离线必需检查与联网探针拆为独立任务；需要安装依赖时依照锁文件，不能在每次 CI 临时解析最新版。若使用外部 Actions，固定完整提交 SHA，并记录升级流程。报告保存测试总数、失败数、环境、代码 SHA、构建标识；需要下载产物时先验证工具是否能取得，不能只假设 artifact 已可访问。

必须检查：正确工作流触发范围、PR/SHA 对应、失败退出码、日志可读、超时、无生产 Secrets、无任意写仓库权限。静态检查不调用网络；只读网络失败单独标记，不能导致无关单测被跳过而显示整体通过。

交付：可复现安装与构建、实际 CI 运行、版本清单、报告和小范围 PR。禁止：业务页面、六工具实现、Cloudflare 资源创建、真实钱包操作。

### M0-C：Workers/D1/R2/Queues 最小运行时验证

使用官方支持的 Workers 测试能力验证实际运行时绑定，而不是只用 JavaScript mock 代替全部测试。[S3]

测试内容：D1 batch 回滚；条件更新未命中时不发生后续错误写入；事件去重与 outbox；R2 写入/读取/hash/应用权限检查；队列重复、重试、定时事件；API 404 不返回 SPA 的 HTML 200。

边界：本地绑定通过不证明真实账号、Cloudflare 云端限额、私有 S3 预签名访问都通过，云端项目在 D1 验证。

### M0-D：Arc 最小真实兼容验证

使用专用测试钱包与测试币，验证 approve/transfer/transferFrom、精度、成功/失败 receipt、实际日志、SDK 合约调用、EOA 与声明支持的合约钱包签名。只部署最小兼容性测试合约，不开发六工具。

对无法安全复现的网络边缘状态，例如特定地址冻结，记录模型测试与真实测试差别；不得要求或尝试冻结真实用户地址。浏览器钱包的完整产品交互留到 M2，不在此假装已完成全站登录。

需要单独确认测试钱包与测试币操作范围。不得索取用户主钱包私钥，不向历史探针里的示例地址打钱，不把本地公开测试私钥用于生产。

### M0-E：阶段收口

对照原计划与新拆分，列出每项 PASS/FAIL/BLOCKED/NOT RUN、环境、实际证据和转移到后续阶段的项目。更新 PR #1 过时正文；逐个明确需要合并的提交范围。

只有本阶段验收通过并经用户确认后才合并对应代码。可以将已验证的 CI 底座与仍待执行的技术探针分为小 PR，但未执行项目必须保留明确追踪，不借拆 PR 把 M0 伪装为全部完成。

## 6. M1 与 M2：先见到产品，再补齐共享底座

### M1-A：视觉基准

确认首页/工具详情、创建向导、付款与凭证页、工作区四类视觉基准；浅色、模块化、必要的局部磨砂，不用宣传拼图代替实际页面。桌面和手机都检查，优先让人理解用途和下一步。

### M1-B：网站骨架

实现目录、导航、六工具介绍、草稿向导壳、双语、空态/错误态。只有演示数据，明确 Demo/Preview，真实付款开关关闭。用户点击进入不同工具应能理解流程，不能只有六张卡片加“即将推出”。

### M1-C：预览验收与 D0

通过视觉和浏览器检查后，按 D0 创建最小 Cloudflare 预览。拿到真实 URL、Worker 版本和实际截图。此时无需搭齐全部数据库和队列；不得把网页能打开称为业务已上线。

### M2-A：身份、工作区与权限

SIWE 登录与 session、nonce/过期/域校验、角色、跨工作区对象权限、草稿版本和审计。浏览无需钱包，参与者不必创建商家工作区。登录签名与资金签名分开。

### M2-B：订单与链上同步

Intent、金额整数处理、规则快照、交易计划、receipt 验证、业务事件、游标、补扫、ledger 投影和 outbox。区分授权/付款/交付/领取状态；不能凭截图或等额 Transfer 解锁。

### M2-C：文件、任务与后台

私有文件、不可变版本、限时访问、上传检查、任务重试/死信、通知、操作日志、故障与恢复页。文件安全扫描尚未落实时，仅允许受控文件，不开放任意用户上传。

### M2-D：D1 云端联调与安全回归

在独立测试资源验证数据库、文件授权、Queues/Cron、RPC 可达性和日志；真实钱包登录/切链/拒签/刷新恢复；使用最小测试合约验证索引，不冒充已部署正式工具。配置基础成本告警和恢复方法，从此后每个工具使用同一套稳定测试环境。

## 7. 六工具统一拆分方式

每个工具原则上按四次小交付推进，可按代码量进一步拆分，而不是一次写完整工具：

| 子阶段 | 工作范围 | 结束证据 |
|---|---|---|
| A：规则与合约 | 确认业务规则；定义状态/权限；实现本工具合约及金额测试 | 条款卡、ABI、单元/模糊/不变量测试 |
| B：服务与同步 | API、数据库增量迁移、索引投影、任务 | API/权限/重试测试、可重放事件证据 |
| C：页面与交互 | 创建者/参与者/管理页、钱包、错误与恢复状态 | 实际渲染、移动端、浏览器测试 |
| D：测试网交付 | 部署测试实例，前后端和链端联调，负面场景，旧工具回归 | 部署清单、真实交易、截图/日志、验收 PR |

编写合约前可先在 A 中用小决策卡澄清关键条款，不把大量未确认问题留到最后。B/C 依赖已确认的接口，合约变化必须同步 API/事件/前端类型。不能为了让联调通过删除失败断言或绕过权限。

### M3 Split 的范围与验收

成员签同一比例与余数规则 → 激活 → 实际入金 → 分配 credit → 每人领取。测试拒签、重复成员、比例总和、微额舍入、重复来源、收款失败保留 credit、第三方代触发不能换收款人。先将资金分配基础验证可靠，再允许其他工具调用。

### M4 Deliver 的范围与关键决策

商品版本、R2 文件、订单、交付可用证明、退款和结算；来源结算成功后才进入 Split。

必须确认：下载后仍允许无条件退款的业务代价；交付超时/退款/文件保留时间；证明角色与受限执行预算；版权及恶意文件处理。不能只做成功下载，还要模拟文件失效、证明服务停机、退款与结算竞争。

### M5 Group 的范围与关键决策

付费席位、容量竞争、截止判定、退出、失败/组织者取消退款、资料权限、收入释放和 Split。

必须确认：门槛按席位而非已验证自然人数；成功成团后的取消/履约争议规则；资金何时释放。测试未满额、刚好满额、最后一席并发、先退出后重报、Cron 不运行仍能执行结果、退款负债不会被结算走。

### M7 Rewards 的范围与关键决策

名单校验、固定编码与 root、足额资助、个人资格/proof、一次性分配和领取、到期回收未分配金额、备份恢复。

必须确认：是否公开名单、领取期限、未领取的回收目的地、名单复核人。测试过期、错误 proof、换链/换期重放、已形成 credit 但未到账时不被出资人回收。

### M8 Attend 的范围与关键决策

报名保证金、动态签到、工作人员核验、补录、缺席提议、挑战、裁决、超时退款及现场演练。

必须确认：谁证明到场、谁处理争议、其可用性/利益冲突、期限、缺席款归属。没有真实可用处理方时不得开放带没收逻辑的公众主网活动。扫码成功、链上确认和退款到账必须是不同状态。

### M9 Milestones 的范围与关键决策

双方签约、只为当前阶段入金、提交/修订、验收/超时、争议、双方和解、预先确认 fallback、私有证据。

必须确认：无响应放款规则、修改次数/截止、仲裁人、超时分配比例。fallback 是双方预设退出规则，不代表平台裁定谁对谁错。未确认角色/比例时不能激活真实资金合同。

## 8. 四个部署检查点

### D0：无资金网站预览（M1 后）

输入：M0 底座、M1 骨架和视觉确认；Cloudflare 账号授权、最小资源范围与费用预期已明确。

工作：创建专用预览 Worker，部署 Static Assets 和必要路由；可先使用实际账号提供的 workers.dev 域名；配置构建版本、日志、缓存和回退。没有默认创建全部收费服务，也不购买正式域名。

验收：真实 URL 可用、响应式检查、错误路由、明确 Demo、无法发送主网资金交易、回退上一个 Worker 版本成功。

### D1：测试环境（M2 收口并持续用于 M3—M9）

输入：D0 和共享平台；专用测试网钱包、测试币、受限云端凭证。

工作：创建 testnet 专用 Web/API、Jobs、必要证明服务、D1、私有 R2、Queues/DLQ、Cron；最小权限 Secrets；配置测试网 RPC/部署清单；受邀用户访问、备份、日志和告警。

验收：D1 事务与迁移真实可用；R2 私有访问而非公开桶；queue 重放/DLQ/Cron 实测；Worker 能访问 Arc；wallet→API→chain→indexer→业务状态闭环；数据库/R2/密钥不共用生产环境。完整路径每次记录 source SHA、网络、部署地址与实际交易。

后续每个工具完成 D 子阶段才部署其测试网实例，不一次提前部署六个空壳合约。共享数据库迁移须回归已经完成的工具。

### D2：三工具受控主网试运行（M6）

前置：M3—M5 联调和资金安全测试；独立安全审查问题闭环；文件/退款/合作规则落实；生产角色、账号、预算、域名策略、监控、恢复和主网操作范围明确获批。

工作顺序：冻结候选源码/ABI → 对应版本审查 → 创建隔离生产资源 → 应用兼容数据库迁移 → 独立批准并部署资金合约 → 核验网络/地址/源码/角色 → 配置清单 → 部署后端/索引再前端 → 小额内部付款、退款、领取 → 对账 → 批准开放受邀业务。

上线范围：只开放 Deliver、Group、Split；其余 Preview。不能把浏览首页的匿名请求当真钱测试，不将内部测试钱包称真实客户。

此阶段可形成参赛版本，但不是六工具项目完成。活动当前要求运行于 Arc 主网，截图和测试网不能替代；提交前重新核验规则。[S6]

### D3：六工具完整发行（M10）

前置：M7—M9 每项测试网验收和各自安全/业务角色门禁；三工具旧生产版本回归。新增功能逐项启用，不要求所有合同一次切换。

工作：候选版本回归、实际域名/政策/客服/使用说明、分批新合约发布、迁移兼容、告警、备份恢复、运维权限移交、源码 tag/ABI/部署清单及最终演示。

验收：六项都能按真实状态完成使用，已收本金有明确出口，旧实例用户仍能退款/领取，出现问题可停新业务而不假装撤销已上链交易。若 Attend/Milestones 缺仲裁或安全条件，允许发行较小范围版本，但不能称“六工具全部上线”。

## 9. M6、M10 的发布工作不是一轮大任务

M6 建议拆：A 三工具回归与故障注入；B 安全问题修复及独立审查；C 生产部署计划和授权；D D2 小额执行和放行；E 可核验演示与参赛资料。

M10 建议拆：A 六工具回归；B 新工具逐项安全放行；C D3 生产批次；D 灾难恢复与旧版本兼容；E 使用/运维文档、tag、上线清单与已知限制。

审查必须对应准确源码/ABI；修复改变了被审查部分时重新检查。自我审查、另一轮 AI 审查或 CI 绿灯不能声称是独立第三方安全审计。

## 10. 发布流水线与权限设计

### 10.1 分支与执行权限

开发采用 main + 短期功能分支 + PR，默认不另外引入长期 dev 分支。测试环境是部署环境，不必对应一个永久 dev 分支。正在进行的 M0 PR 可以按证据继续，但不能覆盖 main 或 force push 他人变更。

CI 是无生产凭证的验证。部署 job 另有受控环境和受限 Cloudflare 凭证；不让 fork PR 或不受信任 ref 访问云端密钥。不要使用 pull_request_target 加载攻击者代码配合 Secrets。

生产部署固定已验收源码 SHA 或不可变构建产物；不得在审批后重新拉分支最新代码冒充同一版本。记录环境配置/迁移版本/ABI/合约地址；网站代码版本与合约模板版本独立。

### 10.2 自动化的边界

可以自动：每次代码变更的检查、离线测试、构建；经批准后更新测试环境；新实例事件同步与有限任务。

需要人工放行：首次账号授权/收费资源、生产部署、主网合约部署/权限更改/额度增加、破坏性迁移、删除数据或已发布文件、规则改变和审计预算。

GitHub 支持环境审批、分支限制和在规则通过后释放环境 Secrets；但只写 environment 名称并不代表真的配置了保护规则，需要实际核验。[S4]

当前 GitHub 连接器以 iwbinb 身份执行。若部署触发者和唯一审批人都是这个账号，盲目开启 Prevent self-review 可能无法完成审批。需要真实第二人时由独立账号担任；一个账号上的 AI 操作和本人操作不能包装成独立双人控制。[S4][R1]

### 10.3 Cloudflare 授权

Actions 调用 Wrangler 的官方路径需要 Cloudflare account ID 与 API token。[S2] 凭证仅通过授权流程或受保护的 Secrets 配置，不发聊天正文、不进 Git、不打印日志。

部署凭证与运行时证明密钥、测试钱包、生产部署/管理钱包分离。权限按实际可支持的账号/资源范围最小化；无法细到单个资源时需明确剩余权限面及隔离方案，不能声称天然只能操作 ArcBox。

到首次云端授权时先检查当时可用的连接工具及支持范围；确实需要用户点击授权、设置秘密或钱包签名时暂停说明最少操作，不预先承诺无需用户介入即可部署全部内容。

## 12. 每次结束的统一汇报

建议固定六项：本次子阶段；交付了什么；实际测试与准确 SHA；PR/合并状态；部署环境及真实地址（没有则明确没有）；阻塞、需确认事项和唯一下一子阶段。

状态须分维度记录：

| 维度 | 示例 |
|---|---|
| 实现 | 未开始 / 开发中 / 代码待审 / 已验收 |
| 测试 | NOT RUN / PASS_LOCAL / PASS_CI / PASS_TESTNET / FAIL |
| 代码归属 | 分支/PR/准确SHA；未合并/已合并 |
| 部署 | 无 / Preview / Testnet / 受控Mainnet / 已批准公开 |
| 业务门禁 | 待规则确认 / 待角色 / 待审查 / 已放行 |

测试结果只能对应实际运行的代码与环境。一个只读 Actions 成功不代表整个 M0 通过；工具测试网通过不代表生产已部署；钱可领取不等于已到账。

## 13. 不得省略的跨阶段测试

合约：金额守恒、防重入、权限、签名重放、精度、截止前后、失败转账、已有 credit 的退出；各工具现有验收清单持续沿用。

后台：数据库事务/CAS、重复/乱序事件、outbox/队列、RPC 中断、索引补扫、任务失败重放、未授权对象访问、环境隔离。

前端：真实钱包与 mock 区分、授权/付款分开、拒签、刷新恢复、付款成功但业务待处理、移动端、双语和键盘。

文件/隐私：私有桶、hash、上传检验、过期 URL、退款后新授权撤销、不得承诺已下载文件可回收、名单/争议证据不可枚举。

生产：构建版本准确、部署签名与运行时角色隔离、少量真币完整进出、已启用功能回归、限额/告警/日志、备份恢复和停新业务演练。

## 14. 运维交付与失败处理

D0 开始建立日志和版本；D1 开始任务/索引/文件告警与测试数据备份；D2 前完成生产预算和资金对账告警；D3 前演练恢复并交付责任清单，不能上线后才考虑监控。

回滚分三类：网站/Worker 可回到先前已验证版本；D1 迁移采用兼容扩展与独立恢复；链上交易不能因回退数据库而撤销。旧不可升级实例保留既有退出路径，新逻辑用新版本，不自动迁走用户资金。

平台停止服务时，链上权益与链下文件/proof 依赖分别说明。用户恢复包应包含自己的订单/合约/规则/证明，不能泄露他人数据。

维护不是本助手在没有任务时持续后台巡检。本项目可部署受控的 Cron、告警和 CI 自动化；后续人工复核、问题处理和版本升级按新的明确任务执行。
